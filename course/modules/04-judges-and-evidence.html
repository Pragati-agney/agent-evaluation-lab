04

Judges and Evidence

Using one AI to grade another, and how two judges together tell you why an answer went wrong

When a checklist can't read

"B-104 is on revision C," "Part B-104: rev C," and "It's currently at revision C" all mean the same thing. A rule like "does the text equal X?" would fail two of them.

So the last two graders are LLM-as-a-judge checks: a second AI model reads the answer and returns a verdict. Both use gpt-4.1-mini with temperature 0 and a structured form, just like the supervisor.

Two judges, two different questions

Think of a newsroom. One editor compares a story with what really happened. A second editor checks every sentence against the reporter's own notes. Same story, two very different questions.

✅

answer_correctness

"Is the answer right?" Compares the answer with the answer key's reference answer. Different wording is fine; a changed fact is not.

📎

groundedness

"Did it stick to its evidence?" Compares the answer only with what the tool returned in that same run. It never sees the answer key.

🧾
Why "the same run" matters

The evidence is the tool's actual reply from the run being graded, pulled off the shared notepad. If the judge used a stored copy instead, it couldn't tell what the agent really saw.

The groundedness judge refuses to guess

What if there's no evidence at all? This experiment only contains PLM questions, so every good run must have tool results. The code in evals/run_langfuse_experiment.py treats "no evidence" as a failure instead of asking the AI to guess:

CODE 
def groundedness_evaluator(*, input, output, **kwargs) -> Evaluation:
    # This experiment is PLM-only, so every answer should rest
    # on tool evidence; without any, fail instead of guessing.
    if not output["tool_results"]:
        return Evaluation(
            name="groundedness",
            value=0,
            comment="No tool results in this execution to ground the answer.",
        )

💡
Fail loudly, with a reason

A grader that quietly guesses can hide bugs. This one fails on purpose and leaves a comment explaining why. When you ask AI to build checks, ask for "explicit failure with a reason" rather than a silent default.

A planted failure: revision D

To prove the judges work, the project includes a fire drill. evals/simulate_failure.py temporarily swaps the lookup tool for a broken one that says revision D instead of C, just for one run. The real tool is untouched.

CODE 
def corrupted_part_metadata(part_id: str) -> dict:
    # Simulated fault: the PLM lookup reports revision D
    # instead of C, so the agent answers from bad data.
    return {**original_func(part_id), "revision": "D"}
