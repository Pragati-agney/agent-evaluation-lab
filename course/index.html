How an AI Agent Gets Graded
01

One Question, End to End

What this project does, and what really happens when you ask its AI a question

An AI assistant, plus a strict exam for it

This project has two halves. One half is an AI agent that answers engineering questions, like "What revision is part B-104 on?" The other half is an exam that grades every answer the agent gives.

The exam is the real star. Anyone can wire up a chatbot. Knowing for certain it still works after every change is the hard part.

🤖
The agent

Reads a question, decides who should handle it, looks up data, writes an answer

📝
The graders

Six checks that score every answer: some are simple rules, two are AI judges

🚧
The gatekeeper

Blocks any code change from going live if a single grade drops

Think of a parcel sorting depot

When a parcel arrives at a depot, a sorter reads the label and sends it down the right conveyor belt. Nobody opens every parcel; one person decides where it goes, then a specialist handles it.

Your question is the parcel. A supervisor reads it and sends it to one of four belts:

📐

cad_agent

Change shapes and sizes: "make bracket A 3 mm thick"

🌡️

simulation_agent

Run tests on a design: "run a stress simulation"

🗂️

plm_agent

Look up a part's history: "what revision is B-104 on?"

❓

clarify

Too vague to sort: "check bracket A." Ask for more detail

🔎
Only one belt is "real" today

The CAD, simulation and clarify specialists are placeholders that reply with a fixed sentence. The PLM agent is the only one that actually looks data up, so that's the one we'll follow.

The sorter's decision, in real code

Here's the exact code that reads the supervisor's choice and picks the next box. It's the "which conveyor belt?" moment from app/graph.py.

CODE 
def route_after_supervisor(
    state: AgentState,
) -> str:

    decision = state["routing_decision"]

    if decision is None:
        return "clarify"

    return decision.route
PLAIN ENGLISH

Define a function called "route after supervisor"...

...that receives the agent's state (its shared notepad)...

...and hands back a piece of text: the name of the next box.

 

Read the supervisor's decision off the notepad.

 

If there's no decision at all (it's empty, which Python calls None)...

...play it safe and send the question to "clarify".

 

Otherwise, go wherever the supervisor said: for our question, "plm_agent".

💡
Always have a safe default

Notice the fallback: if the decision is missing, the question goes to "clarify" instead of being sent somewhere random. Engineers call this failing safe. It only covers a missing decision, though. If the AI service itself is down, that call errors out before this code runs. When you ask AI to build routing logic, ask: "what happens if the decision is missing, and what happens if the AI call fails?"

Why grade an AI at all?

Normal code is predictable: same input, same output, every time. An LLM isn't. Tweak one sentence of its instructions and it might start sending stress questions to the CAD agent.

→
3

Any wrong answer blocks the change

That loop is what the rest of this course unpacks: who the actors are, how the grading works, and how the gate gets enforced.

Every file has one job. Knowing who does what lets you tell AI exactly where a change belongs.

The supervisor fills in a form, not a letter

Picture a hospital triage nurse. They don't write the doctor an essay; they tick one box on an intake form: cardiology, orthopaedics, or "needs more info." A tick box can't be misread.

The supervisor works the same way. Instead of free text, the AI must return a structured output that matches this form from app/models.py:

CODE 
class RoutingDecision(BaseModel):
    route: Literal[
        "cad_agent",
        "simulation_agent",
        "plm_agent",
        "clarify",
    ]

    reason: str
PLAIN ENGLISH

Define a form called "RoutingDecision", built on Pydantic's form template (a class).

Field one, "route", must be exactly one of these choices (Literal):

the CAD specialist,

the simulation specialist,

the PLM specialist,

or "ask the user for more detail."

End of the allowed choices.

 

Field two, "reason": a short free-text explanation of the choice (a string).

💡
Forms are what make grading possible

Because the route is always one of four exact words, a grader can check it with a simple "does it equal plm_agent?" That's impossible with an essay. When you want to test an AI feature, first ask your AI tool to make its output structured.

The tool: how the agent touches real data

An LLM only knows what it was trained on; it has no idea what revision B-104 is on today. A tool is a function the AI is allowed to call to look things up. Here's the one in app/tools.py:

CODE 
@tool
def get_part_metadata(part_id: str) -> dict:
    """Get PLM metadata for an engineering part.

    Use this tool when information about a part's revision,
    lifecycle state, or version is required.
    """

    # Fake enterprise system for our lab.
    # Later this could be Teamcenter, a REST API,
    # database, connector, etc.
    return {
        "part_id": part_id,
        "revision": "C",
        "lifecycle_state": "Released",
        "version": "3.2",
    }
PLAIN ENGLISH

Mark the next function as a tool the AI may call (this "@" line is a decorator).

The tool takes a part ID (text) and returns a dictionary of facts.

This description (a docstring) is read by the AI...

 

...to decide when this tool is worth calling: revisions,

lifecycle states, or versions.

End of the description.

 

A note for humans (a comment): this is fake data for the lab...

...in real life this would call a PLM system like Teamcenter or a REST API.

 

Hand back the facts:

the part ID that was asked about,

revision C (always, in this lab),

version 3.2.

03

The Checklist Examiner

How an answer key and a handful of simple rules catch most agent mistakes, with no AI needed to grade

A driving test, not a pop quiz

A driving examiner doesn't ask you to recite the highway code. They sit beside you with a checklist: checked mirrors ✓, stopped at the red light ✓, parked inside the lines ✓. Each item is a plain yes or no.

The first four graders in this project work exactly like that. They're deterministic: plain code that answers yes or no, the same way every time.

🧭

route

Did the supervisor pick the expected specialist?

🔧

required_tools

Did it call every tool it was supposed to?

🎯

required_tool_args

Did it look up the right part, with the right inputs?

🔢

max_tool_calls

Did it finish without calling tools over and over?

The answer key: a "golden dataset"

Every exam needs an answer key. Here it's called a golden dataset: a list of questions plus what a correct run should look like. It's stored as JSON in evals/graph_dataset.json.

CODE 
    "constraints": {
      "required_tools": ["get_part_metadata"],
      "forbidden_tools": [],
      "required_tool_args": {
        "get_part_metadata": {"part_id": "B-104"}
      },
      "max_tool_calls": 2,
      "answer_must_mention": ["B-104", "C"]
    },
PLAIN ENGLISH

The rules a good run must follow for this question:

It must use the part lookup tool at least once.

There are no banned tools (yet).

When it looks something up...

...at least one lookup must ask about part "B-104", not some other part.

 

It may call tools at most twice in total.

The answer should mention B-104 and revision C (written down, but not graded yet).

End of the rules.

Rules about behaviour, not a script

Notice what the answer key doesn't say: it never lists "call tool A, then tool B, then answer." Compare the two ways you could give someone directions:

🗺️
Turn-by-turn script

"Left on Main St, right on 5th, park at number 12." One roadworks detour and you've "failed", even though you arrived.

📍
Behavioural rules

"Arrive at number 12, avoid toll roads, under 20 minutes." Any sensible route passes; only real mistakes fail.

AI agents take slightly different paths each run. Checking behaviour (right tool, right part, not too many calls) instead of an exact sequence keeps the test from failing on harmless variation, which engineers call a flaky test.

One checklist item, in real code

Here's the required_tools check from evals/evaluators.py. It's just three meaningful lines.

CODE 
def required_tools_called(
        required_tools: list[str],
        tool_calls: list[dict],
) -> bool:
    called_tools = {tool_call["name"] for tool_call in tool_calls}
    return set(required_tools) <= called_tools
PLAIN ENGLISH

Define a check called "required tools called". It takes:

the list of tool names the answer key requires,

and the list of tool calls the agent actually made.

It answers yes or no (a boolean).

Collect the names of every tool the agent called into a set (duplicates removed).

Answer yes if every required tool is somewhere in that set. Extra tools are fine; missing ones are not.

💡
Cheap checks first

These checks cost nothing, run instantly and never disagree with themselves. Good evaluation stacks them first, and only reaches for an (expensive, occasionally inconsistent) AI judge for things rules can't check, like "is this answer true?"

The other exam: routing accuracy

A second, simpler exam tests the supervisor on its own with 7 questions across four categories called slices. The pass marks live in evals/config.py:

CODE 
MIN_OVERALL_ACCURACY = 0.90

MIN_SLICE_ACCURACY = {
    "cad": 0.80,
    "simulation": 0.80,
    "plm": 0.80,
    "ambiguous": 0.80,
}
PLAIN ENGLISH

Overall, at least 90% of routing questions must be right.

 

And within each category, at least 80% must be right:

CAD questions,

simulation questions,

PLM questions,

and deliberately vague questions.

End of the pass marks.

⚠️
Small exams are strict exams

With only 7 questions, a single miss means 6/7 = 85.7%, below the 90% bar. And each category has just 2 questions, so one miss drops it to 50%. One wrong answer fails the whole exam.

04

Judges and Evidence

Using one AI to grade another, and how two judges together tell you why an answer went wrong

When a checklist can't read

"B-104 is on revision C," "Part B-104: rev C," and "It's currently at revision C" all mean the same thing. A rule like "does the text equal X?" would fail two of them.

So the last two graders are LLM-as-a-judge checks: a second AI model reads the answer and returns a verdict. Both use gpt-4.1-mini with temperature 0 and a structured form, just like the supervisor.

1

The agent produces an answer

→
2

A judge AI gets the answer plus a rubric

→
3

It fills in a form: yes/no plus a one-sentence reason

→
4

Yes becomes score 1, no becomes 0

Two judges, two different questions

Think of a newsroom. One editor compares a story with what really happened. A second editor checks every sentence against the reporter's own notes. Same story, two very different questions.

✅

answer_correctness

"Is the answer right?" Compares the answer with the answer key's reference answer. Different wording is fine; a changed fact is not.

📎

groundedness

"Did it stick to its evidence?" Compares the answer only with what the tool returned in that same run. It never sees the answer key.

🧾
Why "the same run" matters

The evidence is the tool's actual reply from the run being graded, pulled off the shared notepad. If the judge used a stored copy instead, it couldn't tell what the agent really saw.

The groundedness judge refuses to guess

What if there's no evidence at all? This experiment only contains PLM questions, so every good run must have tool results. The code in evals/run_langfuse_experiment.py treats "no evidence" as a failure instead of asking the AI to guess:

CODE 
def groundedness_evaluator(*, input, output, **kwargs) -> Evaluation:
    # This experiment is PLM-only, so every answer should rest
    # on tool evidence; without any, fail instead of guessing.
    if not output["tool_results"]:
        return Evaluation(
            name="groundedness",
            value=0,
            comment="No tool results in this execution to ground the answer.",
        )
PLAIN ENGLISH

Define the groundedness grader. It receives the question and the agent's output (and ignores anything else it's handed).

A note explaining the reasoning:

no evidence on a PLM question means something went wrong.

If the run produced no tool results at all...

...immediately hand back a score, without calling the judge AI:

named "groundedness",

worth 0 (fail),

with a note saying exactly why, so a human reading the results understands.

End of the early exit.

💡
Fail loudly, with a reason

A grader that quietly guesses can hide bugs. This one fails on purpose and leaves a comment explaining why. When you ask AI to build checks, ask for "explicit failure with a reason" rather than a silent default.

05

The Gatekeeper

How every grade gets recorded, and how a failing grade physically stops a code change from going live

A flight recorder for every run

After a plane incident, investigators don't guess; they read the black box. Every input, every reading, in order. Langfuse is this project's black box. Every agent run is saved as a trace.

🧵
Traces

Step-by-step recordings: supervisor → PLM agent → tool → answer. In the revision D drill, the tool step visibly shows "revision: D" going in.

📚
Dataset

A copy of the answer key stored in Langfuse, called agent-evaluation-lab

🧪
Experiments

Run the agent over every dataset question, attach all six scores to each trace, and compare runs side by side

The one number that controls everything: the exit code

When a program finishes, it quietly reports a number to whoever started it: an exit code. 0 means success; anything else means failure. Both exams end the same way:

CODE 
if __name__ == "__main__":
    passed = run_experiment()

    if passed:
        sys.exit(0)

    sys.exit(1)
PLAIN ENGLISH

Only when this file is run directly (not borrowed by another file)...

...run the whole experiment and get back "did everything pass?"

 

If every check passed...

...finish with exit code 0: "all good."

 

Otherwise, finish with exit code 1: "something failed." This is what blocks the change.

⚠️
Printing "FAIL" isn't enough

A script can print a big red "FAIL" and still exit with 0. Automation only listens to the exit code, so it would happily wave the change through. If you ask AI to "make the tests fail the build," check that it actually exits non-zero.

Lessons learned the real way

These all happened while building this project, and each one is a pattern worth knowing.

🔑

Missing keys → red, not green

The first CI run failed with UnauthorizedError: the Langfuse keys hadn't been added yet. Good! A misconfigured gate must fail closed, never wave changes through.

👻

Silent drop-outs

The Langfuse SDK quietly leaves out questions that crashed. So the gate counts results and demands every score exists; otherwise an empty run could "pass".

🔄

Two copies of the answer key

CI reads the dataset in Langfuse, not graph_dataset.json. Edit the file and forget to re-run the upload script, and CI keeps testing the old questions.

📋

Two copies of the prompt

The supervisor's instructions exist in both supervisor.py and graph.py. Change one and the other exam keeps testing the old version.

💡
A gate is only as strong as its weakest "pass"

Most gate bugs aren't false alarms; they're false passes: missing data, skipped checks, a print instead of an exit code. When reviewing AI-built tests, ask: "is there any way this could pass without actually checking anything?"

The whole picture

You've followed one question from the keyboard to a locked Merge button. Here's the full system in one glance.

1
The agent answers

2
The checklist grades the process

Right route, right tool, right part, not too many calls: four cheap yes/no rules

3
The judges grade the answer

4
The gate enforces it

Langfuse records everything; GitHub Actions turns any failing score into exit code 1; the ruleset blocks the merge
